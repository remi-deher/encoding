# Corrections consécutives à l’incident du 27 octobre

Ce document distingue les changements de code des opérations de production. Aucune réparation des bases de production, modification de comptes réels, modification des ACL ou intervention TrueNAS n’est incluse.

## Changements implémentés

- `flow_draft_backups` est immuable dans la projection. Un instantané identique est acquitté sans UPDATE ; les champs locaux (`status`, échéances et vérification) restent intacts. La comparaison JSON ignore l’ordre des propriétés. Une définition différente pour la même clé conserve la ligne locale et l’événement en attente, avec `immutable_snapshot_conflict`. Ce conflit n’est plus retenté automatiquement : il exige une investigation et une résolution explicites ; aucun endpoint n’écrase l’instantané.
- La migration additive `0058_projection_diagnostics.sql` crée une table **locale, non réconciliée** de diagnostic. Elle ne contient ni payload, ni SQL, ni message d’exception. Le journal reste conservé. Les erreurs de contraintes, collisions de noms, dépendances manquantes et indisponibilités de stockage sont distinguées. Un avertissement est émis lors du premier échec ou d’un changement de cause, pas à chaque tentative.
- `/api/v1/cluster/reconciliation/status` conserve ses champs et ajoute `projections` et `attributionBlockers`. Le bandeau du cluster montre la cause, la table, la date du premier échec et l’action attendue. Le défaut de confirmation sortante d’un pair est explicite, même sans projection en attente. Les barrières d’attribution restent inchangées.
- Les plugins Plex, Sonarr, Radarr et Jellyfin présents sous `/opt/encoding/plugins` sont découverts depuis leurs manifestes. `Runtime:BundledPlugins:Enabled=false` les désactive tous ; `Runtime:BundledPlugins:<id>:Enabled=false` désactive une intégration. `Runtime:Plugins` continue de primer ; `Enabled=false` sur une déclaration explicite désactive cette déclaration. Une présence sur disque n’annonce aucune capacité avant le handshake existant sous Landlock. La configuration du service distant demeure obligatoire.
- À l’attribution, les champs obligatoires des configurations effectives des plugins référencés sont vérifiés avant le travail média. Une absence échoue explicitement avec le code `plugin_configuration_missing`, le bloc, le plugin et le champ concernés, sans leur valeur. Aucune branche ni protection n’est désactivée.
- Avant le traitement sur un accès source nécessitant l’écriture, le processus vérifie création, écriture, relecture, renommage et nettoyage dans un sous-dossier temporaire dédié. Si `.encoding-results` existe, la sonde utilise ce répertoire ; sinon elle vérifie sa racine future. Une nouvelle vérification a lieu à la publication. Aucun média existant n’est touché et aucun droit n’est accordé par la sonde.
- Les champs optionnels `verifyPublicationAccess` des baux et transferts sont additifs. Les anciens workers les ignorent : ils n’offrent donc pas ce contrôle préventif. Le contrôle ne garantit pas les droits futurs et ne vérifie pas toutes les ACL du remplacement de source ; les contrôles et gardes de publication restent nécessaires.
- Le pipeline reste lisible lorsque l’historique contient des étapes mais une définition de flow partielle. Les étapes gardent leur identité et leur état ; aucune complétion n’est inventée. Les messages de préparation/transfert et de publication sont distincts. Cela couvre un cas de HTTP 500 reproduit en test, sans prouver qu’il était la cause exacte du 500 de production.

## Complément livré : rattachement, politique explicite et observation

- Le rattachement d’une installation initialisée reçoit une liste publique UUID/nom signée, liée au cluster et au pair destinataire. Les collisions `admin`/`ADMIN` suspendent l’adoption locale. Paramètres > Utilisateurs présente le nom d’accueil conservé, suggère un nom entrant libre et demande une confirmation explicite. Une précondition sur le nom courant refuse une décision périmée ; mots de passe, droits, UUID et sessions sont conservés. Un ancien hôte dépourvu de liste signée doit être mis à jour avant le rattachement d’une installation possédant des comptes. La table `cluster_join_user_collisions` (0059) est **locale** et ne contient aucun credential.
- Un défaut de découverte a été identifié dans le code : le rattachement par demande puis approbation perdait l’adresse de réconciliation annoncée. La table `node_peer_reconciliation_urls` (0060), **réconciliée**, la conserve. Elle ne devient une destination candidate qu’après l’admission du pair correspondant. Les réponses restent authentifiées. Un alias réseau qui répond avec la propre identité signée du serveur est exclu. Le statut distingue un échange réussi d’un rattrapage effectivement confirmé.
- La mise en file consulte aussi la propriété réconciliée, y compris lorsque l’historique d’exécution n’a pas encore été projeté. Elle évite ainsi de recréer une demande déjà connue à distance. Une course réelle avant réplication conserve le départage et la quarantaine ; aucun identifiant déterministe commun n’est introduit qui ferait mettre toutes les demandes en quarantaine. L’origine `manual`, `surveillance`, `trigger` ou `api` est enregistrée dans l’historique de création. Les demandes neutralisées restent visibles et ne sont plus comptées comme travail en file (`quarantinedCount`). Les sources historiques d’une demande ancienne ne sont pas inventées rétroactivement.
- L’accès personnalisé utilise le mécanisme réellement disponible sur l’hébergement : un montage ou une ACL préparé sur l’hôte pour cette bibliothèque, sélectionné par son chemin d’accès propre à ce nœud. Le formulaire explique sa configuration, la portée globale des groupes Docker et la différence entre besoins déclarés et droits vérifiés. Aucune élévation ni pseudo-identité UID/GID n’est proposée. Les contrôles préalables incluent aussi le dossier de la source lorsqu’une politique de remplacement est active. Les autorisations propres au fichier (ex. attributs immuables ou répertoire sticky) et leurs évolutions restent vérifiées par l’opération finale ; aucune sonde ne peut promettre une autorisation future.
- Les mécanismes existants `RuntimeHandoffPolicy`, `RuntimeEligibility` et `requireProfileEncoder` sont conservés. Les tests vérifient qu’un nœud sans encodeur peut préparer et céder le segment, que le récepteur doit posséder l’encodeur vérifié du profil et que les transferts/reprises gardent l’accès source et leurs barrières. Aucun NAS ni worker réel n’est inscrit dans les flows générés.
- Le bloc `probe-check-integrity` (`probe` 1.1.0) propose `quick` / `deep` et `auto` / `cpu` / `gpu`. Le mode rapide inspecte structure, pistes, durée et trois passages ; sa limite entre les passages est explicite. Le mode approfondi décode tout l’audio et la vidéo ; le GPU est testé sur le codec et le fichier courants, l’audio reste CPU. Un GPU obligatoire indisponible donne `error`, sans secours silencieux. Sorties : `valid`, `invalid`, `error`.
- Un flow contenant ce bloc exige `media-integrity-policy/v1` sur tous ses workers. La publication exige un contrôle réussi pour le SHA-256 exact ; une autre version du fichier est refusée. Le serveur exige également un checkpoint durable du véritable bloc de contrôle avec la sortie `valid`, indépendamment d’une variable qu’un script pourrait modifier. Les contrôles sont réutilisables pour la même empreinte et les mêmes options, y compris après reprise. Les transferts vérifient toujours leurs empreintes et la publication conserve ses contrôles structurels et son atomicité. Le simulateur demande un résultat supposé sans lire de média.
- Les nouveaux flows guidés et modèles audio/vidéo ont un contrôle rapide explicite avant publication. Les flows historiques sans ce bloc gardent leur décodage intégral obligatoire ; ils ne sont pas modifiés automatiquement. Voir [ADR 0022](../architecture/adr/0022-controle-media-explicite-et-rattachement.md) pour les garanties et la compatibilité entre versions.
- Les commandes commencent à apparaître pendant leur exécution et sont actualisées lors du renouvellement du bail existant, avec progression FFmpeg et durée. Les mises à jour sont bornées, idempotentes par invocation/commande et ne réécrivent pas une étape terminée. Les échecs exposent une cause structurée et, lorsqu’elle est disponible, l’étape concernée. Une publication confirmée durablement est distinguée de l’échec ultérieur d’une intégration.

## Limites de vérification en production

Les lectures HTTP de la production, sans modification, ont montré la version `0.4.110` (`4ddc6df`), des échanges récents, `isolated=false` et `catchingUp=false`. Le second blocage historique après redéploiement n’était donc pas reproductible à cette observation : sa cause exacte n’est pas présentée comme prouvée. La correction du chemin d’adressage et les tests de redémarrage ne permettent pas de réécrire cette conclusion historique.

Aucun déploiement, réparation de comptes réels, contrôle sur les épisodes personnels, modification d’ACL ni validation physique de QSV/NVENC/VAAPI sur TrueNAS n’a été réalisé. Les tests GPU vérifient le refus sans repli lorsqu’aucun décodeur utilisable n’est disponible. La concurrence totalement simultanée avant convergence reste un cas prévu de quarantaine, pas une promesse d’unicité synchrone globale.

## Vérifications

Les tests isolés ajoutés couvrent le rejeu identique/divergent, le statut local, le diagnostic persistant, les plugins livrés et leur désactivation, les prérequis de configuration sans secret, les sondes d’accès et les historiques partiels. Le test existant de redémarrage de la propriété vérifie aussi le diagnostic du pair non rattrapé. Les deux tests UI du bandeau vérifient la cause et le rattrapage manquant.

Les résultats d’exécution sont rapportés dans le bilan de la tâche ; ce document ne revendique aucune validation en production, GPU réel, TrueNAS, déploiement mixte ou traitement des épisodes personnels.

### Résultats locaux

- Compilation backend Release avec `-warnaserror` : réussie, zéro avertissement et zéro erreur.
- Suite runtime complète sur l’état intermédiaire : 514 réussis, 17 ignorés, aucun échec (5 min 35 s). Les modifications suivantes ont été couvertes par les validations ciblées ci-dessous.
- Dernière sélection Release incluant réconciliation, propriété, transferts et nouvelles régressions : 55 réussis, 1 ignoré, aucun échec.
- Lint frontend et compilation Angular : réussis. Deux avertissements de budget SCSS existants (navigation : 17 octets ; catalogue des nœuds : 2 octets).
- Bandeau de diagnostic : 2 tests réussis.
- Rejeu des sauvegardes : test supplémentaire contre la recapture en boucle d’un JSON sémantiquement identique avec un ordre de propriétés différent. Le protocole et les empreintes des événements entrants restent inchangés ; seule l’empreinte d’observation locale conserve la représentation réellement stockée.

### Validation du complément

- Suite runtime complète en Release : **529 réussis, 17 ignorés, aucun échec** (546 tests, 4 min 35 s). Les derniers ajouts de diagnostic sont également couverts par une sélection ciblée après cette suite.
- Scénarios exécutables plugins et déclencheurs : réussis pour les outils disponibles ; les scénarios nécessitant MKVToolNix ou Landlock ont été ignorés sur cette machine. Scénarios du lanceur : réussis.

- Interface : lint réussi, 4 fichiers de tests et **21 tests réussis** ; compilation Angular réussie avec les deux avertissements de budget SCSS existants.
- Ces sélections se recouvrent : leurs nombres ne doivent pas être additionnés. Aucun succès local ne vaut validation sur GPU physique, TrueNAS ou production.
