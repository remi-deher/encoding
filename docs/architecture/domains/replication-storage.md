# Stockage et réplication

## État courant

### Stockage : SQLite local par serveur
- SQLite est le **seul** moteur (PostgreSQL a été retiré ; ne pas le réintroduire sans décision). Chaque serveur ouvre son `cluster.db` (`ConnectionStrings:Cluster`, défaut `Data Source=./data/cluster.db`) : WAL, clés étrangères, délai d'écriture, transactions d'écriture immédiate. **Jamais** de fichier partagé entre hôtes ni sur stockage réseau.
- Constaté en production le 2026-10-21 (lecture seule, deux hôtes TrueNAS) : un seul conteneur `encoding` par hôte, `ConnectionStrings__Cluster=Data Source=/var/lib/encoding-node/cluster.db` monté depuis un dataset local, WAL actif, aucun conteneur ni connexion PostgreSQL pour encoding, aucune erreur `database is locked` dans les derniers logs. La réconciliation passe par HTTP entre les deux nœuds. Migrer vers PostgreSQL n'est pas justifié pour un cluster à deux nœuds (serveur de base supplémentaire à rendre redondant, point de panne commun). Contenu de `cluster.db` non inspecté (`journal_mode` et cohérence entre copies non vérifiés).
- Les dépôts écrivent encore du SQL au dialecte historique (`FOR UPDATE SKIP LOCKED`, `'infinity'`, `clock_timestamp()`, `gen_random_uuid()`, `<@`) : `SqliteTranslator` l'adapte à l'exécution et échoue sur une construction inconnue. Dates en texte UTC de largeur fixe, UUID et JSON en texte. Ajouter une construction SQL nouvelle = étendre le traducteur et ses tests.
- Migrations : `backend/migrations/sqlite/NNNN_description.sql`, **numéro unique** (le chargement échoue sinon), empreinte SHA-256 dans `schema_migrations.checksum` (modifier une migration appliquée bloque le démarrage : en écrire une nouvelle). `MigrationCatalog.RenamedFrom` relie un fichier renommé. Baseline `0033_baseline.sql`, dernière migration connue `0042_system_logs.sql` (vérifier le dossier avant d'en créer : les threads parallèles doivent se coordonner sur le prochain numéro). Une version enregistrée absente du binaire rend le nœud `degraded`.
- `backend/migrations/0036_library_cluster_tombstones.sql` (racine, hors `sqlite/`) n'est pas chargé : reliquat à supprimer ou confirmer.

### Écrivain local (ADR [0009](../adr/0009-ecrivain-sqlite-unique-par-noeud.md))
- `SqliteDataSource`, singleton du serveur, possède une file d’admission locale commune à toutes ses connexions. Les transactions d’écriture y entrent avant `BEGIN IMMEDIATE` et libèrent leur admission après commit, rollback ou fermeture. Les commandes hors transaction y passent aussi, quel que soit leur mode d’exécution ; un lecteur `UPDATE … RETURNING` garde l’admission jusqu’à sa fermeture. L’appelant admis exécute son unité : aucun thread d’exécution dédié ni transfert du code métier.
- Présence (`RecordHeartbeatAsync`) et renouvellement des baux (`RenewAsync`) prioritaires, avec 32 places réservées ; 256 places ordinaires. FIFO dans chaque priorité ; une écriture ordinaire passe après huit urgentes au plus. Attente bornée à 5 s, saturation refusée immédiatement. Ces limites sont configurables sous `Database:Writer`.
- Une transaction reste une unité atomique, sans regroupement de transactions indépendantes (lot = 1). Aucun code métier n’est rejoué. Seul `BEGIN`, avant la première instruction métier, retente deux fois les erreurs SQLite 5/6 (attentes de 25 puis 50 ms, délai SQLite de 1 s par tentative). Une erreur de commande n’est pas rejouée, car un lot hors transaction peut avoir produit un effet partiel.
- `IsolationLevel.Snapshot` ouvre une transaction différée avec `query_only=ON`, réinitialisé à sa clôture : aucune admission d’écriture et aucune promotion en écriture. Les lectures SELECT simples hors transaction contournent aussi la file ; les lots/CTE suivent conservativement l’admission, sans ouvrir de transaction d’écriture implicite.
- La capture et l’application des événements du maillage utilisent les mêmes connexions et transactions : pas de changement de schéma, de journal, d’ordre logique, de déduplication ou de protocole. Baux, réservations et claims restent locaux et atomiques.
- Métriques `encoding_sqlite_writer_*` sur `/metrics` : files, admission active, refus, expirations, tentatives, temps cumulé d’attente/détention et détentions longues ; avertissement Trace après détention supérieure à 1 s. Saturation, expiration et erreurs SQLite 5/6 deviennent HTTP 503 avec code `sqlite_write_unavailable` et `Retry-After: 1`, sans SQL dans la réponse.
- Déploiement par étapes : `Database:Writer:Enabled=false` mesure les unités sans les sérialiser ; `true` active la file dans l’adaptateur commun, d’abord pour les chemins critiques avec `CriticalOnly=true`, puis pour tous les domaines avec `CriticalOnly=false` (défaut final). La phase critique seule conserve des écritures ordinaires directes et ne revendique pas encore l’exclusivité globale. Les migrations et copies de base utilisent aussi cette admission. Exceptions d’infrastructure : initialisation des PRAGMA de connexion, garde `query_only`, commandes brutes de capture Raft dans `PeerDatabaseSchema`. Le mode Raft désactive explicitement la file et conserve son coordinateur existant ; son intégration à cette file reste non livrée. Ne pas ajouter d’accès SQLite brut hors de ces exceptions.
- Les délais bornent l’attente avant admission, pas une transaction déjà engagée. Une annulation en attente retire la demande ; après admission, l’appelant conserve la responsabilité de terminer ou d’annuler sa transaction et la file ne la rejoue jamais. Les transactions longues restent à réduire à partir des mesures. Exploitation et limites : [sqlite-writer.md](../../operations/sqlite-writer.md). Aucune validation sous charge de production ni entre versions mixtes n’est revendiquée.

### Réplication par défaut : maillage de réconciliation (écriture opportuniste, convergence éventuelle)
- Chaque serveur garde sa base ; les serveurs d'un cluster se découvrent par mDNS (`_encoding._tcp`) et par adresses mémorisées (`cluster_sync_peer_endpoints`, gossip transitif, `Cluster:Reconciliation:Peers` en secours) et échangent un **journal append-only** par `POST /api/v1/cluster/reconciliation/exchange` (lots bornés, `(origine, séquence)` déduplique, relais avec origine conservée).
- Un timeout HTTP est un échec du pair : les autres pairs et les cycles suivants continuent. Seule l'annulation du service interrompt le cycle. Une sortie inattendue désactive explicitement l'état de synchronisation avec une raison visible dans `/api/v1/cluster/reconciliation/status` et dégrade le contrôle `cluster-reconciliation` de `/health/details` ; elle ne rend pas la disponibilité locale dépendante des pairs dans `/health/ready`.
- Le rattrapage enchaîne les lots de 32 sans pause tant que les vecteurs indiquent du retard et progressent, même si la limite de 16 Mio a raccourci un lot. Budget par pair et par cycle : au plus 8 échanges et 64 Mio transférés (requêtes + réponses), sans démarrer un échange supplémentaire après 2 s. L'échange engagé garde son timeout HTTP de 10 s ; ce budget de temps ne l'interrompt pas. Sans progression, le pair est laissé au cycle suivant. Les acquittements sont persistés après chaque échange ; le tour continue avec les autres pairs puis attend 15 s. Protocole et signatures inchangés, donc un pair ancien accepte les mêmes lots.
- Conflits : **dernier écrivain gagne par entité** (horodatage UTC, puis origine et séquence), suppressions = tombstones. Les horloges doivent être synchronisées. Une projection en conflit de contrainte unique est gardée en attente.
- Sécurité : identité RSA par serveur, admissions signées répliquées (tout serveur admis peut approuver une jonction), échanges signés, secrets du journal chiffrés AES-GCM avec la clé de données du cluster (créée à la création du cluster, stockée chiffrée sur chaque serveur). Clés privées et Data Protection dans `PluginSettings:KeyDirectory` : à sauvegarder.
- **Réconcilié** : cluster et nœuds (rôles, capacités, présence, groupes), utilisateurs, demandes de jumelage, jetons API, bibliothèques (chemins, accès, limites, politiques de remplacement, inventaire), flows/brouillons/versions, scripts, profils, **métadonnées des ressources de flow** (`flow_resources`, `flow_resource_versions`, migration 0047), modèles, packs, config et dérogations de plugins (secrets rechiffrés localement), historique durable des exécutions (événements, étapes, checkpoints, reçus), réglages IA.
- **Local, jamais répliqué** : baux et réservations, `execution_work`, attentes actives, scans en cours, files de déclenchement, sessions utilisateur, opérations de remplacement en cours, verrous de disque, `system_logs`, paquets du Store de plugins, fichiers binaires (**octets des ressources de flow** : magasin adressé par empreinte `Resources:Directory`, par serveur ; médias, artefacts, sauvegardes JSON régénérées par chaque serveur).
- Conséquence centrale : **aucune exclusion de travail entre bases indépendantes n'est revendiquée**. Une exécution reste attribuée au serveur qui l'a créée ; la reprise après perte est une relance explicite ([runtime.md](runtime.md)).

### Mode pair à pair optionnel (Raft) : prévisualisation
- `PeerCluster__Enabled=true` (défaut `false`) active un mode distinct : trois serveurs votants, journal Raft (DotNext), transactions SQL répliquées par capture de lignes (`PeerDataSource`), baux avec terme Raft, certificats approuvés, port pair séparé. Même version requise sur tous les pairs (pas de N/N-1), image d'import limitée à 64 Mio. Procédures : `docs/operations/peer-cluster-preview.md`, `peer-cluster-production-todo.md`, règles d'alerte `peer-cluster-alerts.yml`.
- **Contradiction à trancher** : ce mode et le maillage LWW ont des garanties opposées (quorum et exclusion forte vs convergence éventuelle sans quorum). Le principe affiché du produit est « sans quorum ». Voir [open-questions.md](../open-questions.md). Ne pas étendre le mode Raft avant décision.

### Sondages de sauvegarde
- La présence d’un travail de sauvegarde dû est consultée sans transaction d’écriture ; le travail est relu sous transaction avant traitement. Un sondage vide ne prend donc pas le verrou SQLite. La publication atomique et les délais de reprise restent inchangés.

### Sauvegardes de flows
- Chaque version publiée et chaque révision de brouillon écrit un travail local dans la même transaction ; `{id}.v{version}.json` est écrit atomiquement (temporaire, flush, déplacement sans écrasement) dans `FlowBackups:Directory` (volume séparé). Un fichier existant d'empreinte différente est conservé et signalé `failed`. Retentative 30 s, revérification 10 min, aucune suppression automatique. Statuts `pending/ready/failed` **locaux** à chaque serveur. Les fichiers sont des instantanés récupérables, pas une autorité d'écriture.
- Restauration : réimport par `PUT` dans l'ordre des versions (identité conservée, `expectedVersion` = précédente) ou import JSON/ZIP ([flows.md](flows.md)).

## Invariants
1. Un fichier SQLite appartient à un seul serveur.
2. Toute nouvelle table métier : décider explicitement « réconciliée » (l'inscrire dans `ClusterEntityReconciliation.Tables`, avec tombstone si suppression) ou « locale » (le documenter ici).
3. Une migration appliquée ne se modifie jamais ; numéro unique ; additive tant que N/N-1 n'est pas garanti.
4. Les secrets ne vont jamais en clair dans le journal, les sauvegardes, les exports ni les journaux.

## Ressources de flow (ADR 0006, PR 1)
- Métadonnées (ressource, versions immuables, noms de fichiers, tailles, SHA-256) réconciliées comme les scripts ; **octets** dans `Resources:Directory` (défaut `<Node:DataDirectory>/resources/ab/<sha256>`), jamais dans le journal : c'est l'exception assumée à l'invariant « binaires jamais réconciliés ».
- Envoi : `POST /api/v1/resources/blobs?kind=font&name=…` (corps brut, un fichier, 20 Mio au plus, extension et signature contrôlées), puis `POST /api/v1/resources` ou `…/{id}/versions` qui référencent les empreintes ; 100 Mio par version. Écriture réservée à `admin`, lecture à tout rôle.
- Suppression : refusée (409) tant qu'un flow, toute version confondue, référence l'identifiant ; le message nomme le flow et le bloc. Un fichier n'est effacé du magasin que si aucune version ne l'utilise encore.
- Récupération par un pair (PR 2) : `GET /api/v1/cluster/resources/blobs/{sha256}`, hors session, authentifié par les identités de pairs admis (mêmes en-têtes et fenêtre d'horloge de 2 min que la réconciliation, limiteur `cluster-mesh`). La signature couvre `GET <chemin>` + pair + horodatage, pas de corps ; la requête rejouée dans la fenêtre ne donne que le même fichier. Réponse en flux avec `Range`. `ResourceBlobFetcher` interroge les pairs connus dans l'ordre, reprend un `.part` à l'octet atteint, vérifie taille puis SHA-256 avant de publier ; un fichier faux est supprimé, un fichier incomplet conservé. Deux demandes de la même empreinte partagent un transfert (délai de 2 min). `ResourcePrefetchService` précharge toutes les 30 s toutes les versions absentes du magasin. Côté worker, un cache local par empreinte (`resources-cache`) est rempli toutes les 30 s avec la dernière version de chaque ressource ; une ancienne version est téléchargée à la demande. La publication d’un flow (PUT) est refusée si une ressource référencée ou sa version n’existe pas.
- Worker (PR 3) : `GET /api/v1/runtime/nodes/{nodeId}/resources/{id}/versions/{n}` (liste des fichiers) et `…/resources/blobs/{sha256}` (octets, récupérés d'un pair d'abord si le serveur ne les a pas), authentifiés par le jeton de nœud. Bloc `subtitles-add-fonts`, champ `resource`.
- Non livré : interface (PR 4).  Un fichier envoyé sans être référencé reste dans le magasin (nettoyage à prévoir).

## Non livré / limites
- Pas de plage de schéma ni de règle de mise à jour progressive entre serveurs.
- Pas de restauration guidée des sauvegardes de flows ; pas de rétention des sauvegardes.
- Les artefacts doivent être sur un stockage accessible aux serveurs concernés (`Runtime:ArtifactDirectory`) ; un volume local n'établit pas de haute disponibilité inter-hôtes.
- Maillage : un changement qui conserve taille et date n'est pas concerné ici (voir sondage de surveillance dans [runtime.md](runtime.md)) ; deux créations isolées de même nom attendent la résolution de la collision.

## Capture incrémentale (ADR [0010](../adr/0010-capture-incrementale-locale.md))
- Migration 0049 : `cluster_sync_capture_tables` (révision source/acquittée) et `cluster_sync_dirty_entities` (dernière révision de chaque clé) sont **locales, jamais réconciliées ni incluses dans les images Raft**. Des triggers INSERT/UPDATE/DELETE suivent les colonnes réconciliées, dans la transaction de l’écriture ; un rollback annule également les marqueurs. Une mise à jour sans changement de valeur ne les active pas.
- Révisions, clés et lignes sont lues dans un Snapshot cohérent. Premier passage ou invalidation = lecture complète de la table ; ensuite, recherche par clés dans les index primaires. Une table stable ne relit aucune ligne métier. Les suppressions restent détectées lorsque la dernière ligne disparaît ; les curseurs temporels conservés pour compatibilité ne filtrent plus cette capture.
- Après traitement, l’acquittement et le nettoyage portent seulement sur les révisions observées. Les nouvelles mutations d’une même clé restent en attente. Les lots déjà validés avant interruption sont dédupliqués par les empreintes au passage suivant. Les révisions sont remises à zéro logique lors de l’adoption d’un autre cluster.
- Les clés des reçus gardent le chemin média portable, normalisé comme les états existants, y compris Unicode. Les mutations d’inventaire invalident le marqueur `scan-inventory/<scanId>` et la capture dépendante des scans/reçus. Les tables locales d’exécution, sessions et baux ne deviennent pas réconciliées.
- Diagnostic Debug `CaptureSelectionRead` : nombre de tables modifiées et de lignes préparées. Test synthétique : pour 1 000 bibliothèques, un passage stable prépare zéro ligne ; la modification d’une bibliothèque prépare une ligne. Cela ne mesure pas la latence de production ni le coût global d’entretien des triggers. Le test du catalogue impose trois triggers par table déclarée ; une nouvelle table/colonne réconciliée doit ajouter sa migration de suivi.
- Les invalidations complètes portent également une révision : une invalidation arrivée après le Snapshot ne peut pas être effacée par l’acquittement d’une lecture plus ancienne. Les transferts/sauvegardes logiques ne recopient pas ces deux tables ; les migrations et les triggers reconstruisent le suivi sur la cible.


## Transactions de capture bornées
- La capture locale valide des lots d’au plus 64 événements et libère l’écrivain entre les lots. Chaque événement, son empreinte d’entité et l’allocation de sa séquence restent atomiques ; un curseur n’avance qu’après le traitement complet de son groupe source.
- Après libération de l’écrivain, les candidats sont revérifiés contre l’état courant et la ligne locale pour ne pas publier un ancien instantané après une projection concurrente. Les suppressions sont confirmées par l’absence de la ligne ; la présence doit toujours correspondre à l’instantané préparé.
- Une interruption peut laisser des lots déjà validés : le passage suivant reprend sans dupliquer les entités inchangées. Les séquences sont relues à chaque nouveau lot. Le format et l’ordre logique du journal restent inchangés ; la borne porte sur les événements, pas sur une durée maximale de transaction.
- Les empreintes des inventaires média sont préparées avant l’admission. Un marqueur local `scan-inventory/<scanId>` dans `cluster_sync_table_cursors` n’est validé qu’après la fin de l’inventaire ; une reprise ne perd donc pas les médias dont le scan a déjà été journalisé dans un lot précédent. Ce marqueur est local et n’est pas échangé entre pairs.

## Index du runtime
- `0048_runtime_lookup_indexes.sql` ajoute des index de recherche des baux et checkpoints, sans nouvelle table ni changement de protocole. Les index sont locaux à la base et reconstruits par les migrations sur chaque serveur ; ne pas les répliquer dans le journal métier. Voir les [plans vérifiés](../../testing/sqlite-runtime-query-plans.md).
